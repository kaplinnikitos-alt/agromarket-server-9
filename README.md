# АгроМаркет API

Backend для учебного проекта «АгроМаркет» на Node.js + Express + PostgreSQL. Отдаёт товары каталогу, умеет создавать, изменять и удалять их (CRUD), принимает оптовые заявки из React-формы, регистрирует пользователей и выдаёт JWT-токены. Изменять каталог и смотреть заявки может только администратор. Frontend: репозиторий `agromarket-react`.

## Запуск

1. Установить PostgreSQL, создать базу `agromarket`
2. Скопировать `.env.example` в `.env` и заполнить значения (см. ниже)
3. `npm install`
4. `npm run db:init`        # создать таблицы, загрузить товары и создать администратора (удаляет данные!)
5. `npm run dev`            # http://localhost:3000

Запускать из папки `agromarket-server` (пути к `db/schema.sql` и `data/db.json` считаются от неё). Нужен Node.js 22+ (флаг `--env-file` и встроенный `fetch`).

## Переменные окружения (.env)

```
PORT=3000
DATABASE_URL=postgresql://postgres:ПАРОЛЬ@localhost:5432/agromarket
CORS_ORIGIN=http://localhost:5173
JWT_SECRET=...        # случайная строка 64 символа
JWT_EXPIRES_IN=2h     # срок жизни токена
ADMIN_EMAIL=...       # администратор, создаётся командой npm run db:init
ADMIN_PASSWORD=...
```

`JWT_SECRET` генерируется командой `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Файл `.env` не попадает в Git, в репозитории лежит только `.env.example` без настоящих значений.

## Лабораторная 7 — ответы

- **Одинаковые ли хэши у двух пользователей с одним паролем:** нет. bcrypt добавляет к паролю случайную соль и хранит её внутри хэша, поэтому у одного и того же пароля каждый раз получается другой хэш. По базе нельзя понять, что у двух пользователей пароли совпадают, и не работают заранее посчитанные таблицы «пароль → хэш».
- **Что вернул сервер на регистрацию с `"role": "admin"`:** 201, но в ответе роль `user`. Маршрут `/register` вообще не читает `role` из тела запроса, роль ставит база через `DEFAULT 'user'`. Так мы защищены от mass assignment: иначе любой мог бы сделать себя администратором.
- **Почему подделанный на jwt.io токен не прошёл:** подпись считается от заголовка и данных с секретным ключом `JWT_SECRET`. Если поменять `role` на `admin`, данные изменятся, а подпись останется старой. Подписать заново без ключа нельзя, поэтому `jwt.verify` не сходится и сервер отвечает 401 «Недействительный токен».
- **Что произошло после порчи токена в localStorage:** при открытии страницы React запрашивает `GET /api/auth/me` с испорченным токеном, сервер отвечает 401, а `apiFetch` при 401 удаляет `token` и `user` из localStorage и перезагружает страницу. Пользователь оказывается разлогинен, снова видна форма входа.
- **Почему спрятать кнопку в React недостаточно:** React-код работает в браузере пользователя, и любой может отправить запрос напрямую (через Console, Postman, curl), минуя интерфейс. Настоящая защита проходит на сервере: `requireAuth` и `requireRole('admin')` отвечают 403 обычному пользователю, что бы ни показывал интерфейс.

## Вопросы для защиты (кратко)

- **Аутентификация и авторизация:** аутентификация отвечает на вопрос «кто вы?» (ошибка: 401), авторизация — «что вам можно?» (ошибка: 403).
- **Хэш, соль, bcrypt:** хэш — односторонняя функция, из пароля его получить легко, обратно нельзя; зашифрованное можно расшифровать, хэш нельзя. Соль — случайная добавка, из-за неё одинаковые пароли дают разные хэши. bcrypt намеренно медленный (cost 10 — около 0,1 с на хэш), поэтому перебор паролей обходится очень дорого.
- **Три части JWT:** заголовок (алгоритм), данные (`sub`, `role`, `iat`, `exp`) и подпись. Первые две части закодированы Base64URL и читаются любым человеком, поэтому пароли и хэши в токен класть нельзя.
- **Подделка токена и утечка JWT_SECRET:** без ключа верную подпись не получить. Если `JWT_SECRET` утечёт, злоумышленник сможет выпускать токены от имени любого пользователя, в том числе администратора, поэтому ключ хранят только в `.env`.
- **requireAuth и requireRole:** `requireAuth` проверяет подпись и срок токена и кладёт в `req.user` id и роль; `requireRole` сравнивает роль. `requireRole` — функция, возвращающая middleware, поэтому её можно настроить на любую роль: `requireRole('admin')`.
- **Одно сообщение при неверном входе:** чтобы по разным ответам нельзя было перебором узнать, какие e-mail зарегистрированы.
- **Mass assignment:** когда в базу попадают поля из тела запроса целиком. Мы защитились в `routes/auth.js`: в INSERT передаются только `name`, `email` и хэш, а `role` не читается из `req.body`.
- **Токен в React:** после входа токен лежит в localStorage, `apiFetch` добавляет его в заголовок `Authorization` каждого запроса, при выходе токен удаляется. Недостаток localStorage: любой JavaScript на странице может его прочитать (атака XSS).
- **Preflight OPTIONS:** перед «непростым» запросом (с `Authorization` или `Content-Type: application/json`) на другой источник браузер спрашивает разрешения запросом OPTIONS. `cors()` отвечает на него сам. Появился он сейчас, потому что мы начали отправлять заголовок `Authorization`.

### Как происходит деплой

1. Изменения — только через Pull Request: CI + ревью
2. Merge в main → CI: test → deploy (Render deploy hook, ref = SHA) → smoke
3. React собирается Vercel из main автоматически
4. Авария: Rollback на Render, затем git revert через PR

### Команды базы

- `npm run db:init` — DROP + CREATE + тестовые данные. Локально, в тестах и CI. На облачной базе — только с `--force` и только на пустой.
- `npm run db:migrate` — `CREATE TABLE IF NOT EXISTS`, данные не трогает; запускается при каждом старте на Render.
- `npm run smoke` — проверки живого продакшена (нужны `API_URL`, `FRONTEND_URL`, опционально `EXPECTED_VERSION`).
